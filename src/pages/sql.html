Modélisation

Du modèle conceptuel à la base

J'ai modélisé les données avant de les coder : un modèle conceptuel (Merise) pour les objets et leurs liens, puis un modèle logique relationnel. Le modèle logique est dessiné à partir de la base elle-même, et le modèle conceptuel est confronté à la base à chaque construction : ils ne peuvent pas diverger du code.

Choix de modélisation

  • Troisième forme normale : l'unité d'un indicateur SCHL dépend de l'indicateur seul ; elle vit dans dim_indicateur, pas dans la table de faits.
  • Dimensions de référence : provinces et types d'estimation sont des tables, avec clés étrangères, plutôt que des codes libres.
  • Grain explicite : chaque table de faits a une clé primaire composée et un commentaire qui décrit une ligne.

Limite assumée

  • « Grande ville » (séries SCHL depuis 1992) et « Région métropolitaine » (estimations trimestrielles) viennent de deux référentiels de Statistique Canada aux identifiants différents. Une table de correspondance serait l'étape suivante.

La même base pour PostgreSQL

Le script loyers_postgres.sql (schéma, vues, données) est dérivé automatiquement des scripts SQLite du projet, pour que les deux versions ne divergent jamais, puis validé par la grammaire de PostgreSQL elle-même (pglast) : une erreur de syntaxe arrête la construction. Cinq écarts de dialecte, et seulement ceux-là :

  • PRAGMA foreign_keys retiré : les clés étrangères sont toujours actives dans PostgreSQL.
  • GLOB remplacé par une expression régulière : periode ~ '^\d{4}-[01]\d$'.
  • REAL devient DOUBLE PRECISION.
  • ROUND(x, n) n'accepte qu'un numeric : ROUND((x)::numeric, n) dans les vues.
  • Une sous-requête dans FROM doit porter un alias.

Télécharger loyers_postgres.sql

Chargement : createdb loyers && psql -d loyers -f loyers_postgres.sql. Le script est aussi dans le paquet de la base. Validation : syntaxe PostgreSQL complète ; l'exécution sur un serveur PostgreSQL n'a pas encore été faite dans ce projet.

Choix techniques

Pourquoi SQLite

  • La base tient en un fichier versionné dans le dépôt et s'ouvre dans le navigateur, sans serveur.
  • Les requêtes restent en SQL standard : elles tournent aussi sur DuckDB, PostgreSQL ou SQL Server avec des ajustements mineurs (POWER, concaténation).

Comment les résultats sont vérifiés

  • src/build_db.py reconstruit la base, exécute les __N_SQL__ fichiers sql/*.sql et compare les résultats clés au pipeline Python, ainsi que deux requêtes entre elles.
  • Un écart (même de 0,05 point) interrompt la construction : aucun chiffre non vérifié ne peut être publié.
